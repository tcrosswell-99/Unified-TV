## Status and test-level mapping

On 25 October 2026 the owner chose the v3.3 developer pack's own status names (`test_passed_nonphysical`, `physical_verified`, `unsupported_verified`) over the interim names (`automated_pass`, `hardware_pass`, `unsupported`); `hardware_fail` and `deferred_preview_only` were dropped (see SPEC.md Section 5). The table below uses the adopted names.

| Old term (v3.2 status, build plan, spec) | New `status` | New `test_level` |
|---|---|---|
| `required_unimplemented_or_unknown`, `spec_only`, "spec-only", "unknown since v0.4" | `not_started` (or `implemented_unverified` once source is audited) | `none` |
| `reported_in_v0.4_source`, `source_inspected`, "partial source claim" | `implemented_unverified` | `none` |
| `implemented_unverified` | `implemented_unverified` | unchanged |
| `unit_pass`, "automated policy/unit tests" | `test_passed_nonphysical` | `unit` |
| `emulator_pass`, "desktop/emulator integration", "simulated Android" | `test_passed_nonphysical` | `simulated` |
| `local_build_pass`, "local build/lint", GitHub Actions build | `test_passed_nonphysical` | `ci_build` |
| `PC_network_observed`, "PC network observation" | `implemented_unverified` (or `blocked`) | `pc_network` |
| `physical_TCL_pass` / `physical_Sony_pass` / `physical_Frame_pass`, `physical_verified` | `physical_verified` (with evidence) | `physical_tcl` / `physical_sony` / `physical_frame` |
| `blocked_external` | `blocked` | as reached |
| `unsupported_verified` (as a status) | `unsupported_verified` | the `physical_*` level that proved it |
| "UNVERIFIED", "unverified" | `implemented_unverified` or `not_started` | as reached |

`supported_verified` / `unknown` remain values of the capability registry (a different field, not a status); `unsupported_verified` is both a capability value and, since 25 October 2026, a register status.
